# Quadra 800 ROM — the startup RAM test, and how the sim skips it

Findings from the 2026-08-28 laptop session (trace runs `--trace-after
78000000 --stop-at-pc 408477e6,408477e7`, registers read off the parked
GUI's Machine panel). Boot cycle counts are from the deterministic
32 MB machine sim.

## Cost: why we care

| phase | cycles | share of a diskless boot |
|---|---|---|
| reset → chime/init | 0–40M | 2% |
| `$40807116` loop = **ROM checksum** (word-sum of the 1 MB image) | 40M–80M | 2% |
| **RAM pattern test** (`$408477xx`–`$40847Axx`) | **80.4M–~1.6G** | **~70%** |
| slot scan, SCSI scan, drivers | ~1.6G–2.31G | 26% |

At ~9 Mcycles/s wall, the test costs ~2.8 minutes of every ~4.5-minute
boot iteration.

## The sequencer and the gate

Startup-test stages live in a fan-in at `$40846F5x`–`$40847080`: each
stage `ori.w #$1N00,d7` stamps a progress code (the death-chime
diagnostic codes), then `lea ret,a6; jmp $40847568(pc)` — pre-RAM
convention, return via `jmp (a6)`. Computed dispatches
(`jmp $4084756c(pc,a0.l)`) defeat the static disassembler; the region
reads as raw bytes in `quadra800-rom-disassembly.asm`. All flow facts
below are from live traces.

The memory-test stage proper:

```
40847336: tst.l  d6                 ; d6 != 0 -> always full test
40847338: bne    $4084734c
4084733C: cmpi.l #'WLSC', (-4,a6)   ; ★ THE GATE: magic 4 bytes below
40847344: bne    $4084734c          ;   the range table -> cold path
40847346: clr.w  d7                 ; warm: progress code 0
40847348: bra    $4084739c          ; warm continuation (skips the test)
4084734C: movea.w #$ffff, a3        ; cold: run the full pattern test
40847350: move.w #$3, d7            ; (the d7=00000003 seen in test HBs)
40847354: movea.l (a7), a4          ; a4 = memory-range table
40847358: movea.l (a4)+, a0         ; {start.l, len.l} entries,
40847360: move.l  (a4)+, d0         ;   $FFFF terminator
...
40847376: jmp $408477d8             ; per-range fill/verify
```

The fill at `$408477D8` marches `movem.l d0-d5,(a2)` with the rotating
3-bit pattern (`$6DB6DB6D/$B6DB6DB6/$DB6DB6DB`), 24 bytes per
iteration; verify passes follow in the `$4084785x`/`$40847Axx` loops.

## The top-of-RAM control block

With 32 MB, the sizing stages (which run BEFORE the gate, every boot)
build the range table at the very top of RAM:

- table base **`$01FFFFA4`** (= 32 MB − $5C); first entry
  `{start=$00000000, len=$01FFFFA4}` — i.e. "everything below me"
- the warm magic is expected at **table − 4 = `$01FFFFA0`**
- the warm continuation (`$4084739C`+) consults MORE of the block:
  a second `'WLSC'` at `(a5+$1E)` (mismatch just sets a flag bit) and
  pointers at `(a5+$26)`

The magic is the stamp the full test leaves on success, which is how a
real machine's warm reboot skips the test. The sim zeroes RAM at every
launch, so every sim boot is a cold boot.

Note: this is NOT the documented low-memory `WarmStart` global at
`$0CFC` — the ROM checks that ('WLSC' too) in the video-init and
driver paths (`$4080433A`, `$40805E12`). `sim.v` has grown a
`+warmstart` plusarg seeding `$CFC` at some point; it never affected
the RAM test because the test reads its own gate at `$01FFFFA0`.

## The skip: a 2-byte patch in a sim-only ROM copy

Forcing the gate means making `$40847344 bne` fall through:

- ROM file offset = `$40847344 − $40800000` = **`$47344`**
- bytes `66 06` (`bne.b +6`) → `4E 71` (`nop`)

The patched image is generated by `make fastboot` into
`quadra800-fastboot.rom.hex` and selected per run with
`+rom=quadra800-fastboot.rom.hex`. `releases/quadra800.rom` is never
modified. The cold-built range table is present by the time the gate
runs (sizing precedes it), so the warm continuation walks real data;
the parts of the control block only the full test writes read as
zeros — the second-'WLSC' mismatch records a flag and continues.

**Scope rule: the fast ROM is an iteration convenience.** Acceptance
gate runs (`--disk` bench boots) use the pristine ROM. Anything that
smells RAM-content-dependent gets rechecked against a full cold boot.

## Verification (2026-08-28)

- First attempt (patch only) died at cycle 53.4M into the death-chime →
  SCC monitor path: the 40M–80M `$40807116` phase is the **ROM
  checksum** (32-bit sum of big-endian words over [4, end), stored at
  offset 0 — algorithm verified against the pristine image:
  `F1A6F343`). The patch must fix the checksum too; delta is exactly
  `$6606−$4E71`.
- With the checksum fixed: diskless boot reaches the flashing-? idle
  loop (`$408014CA`) at **~420M cycles ≈ 47 s wall**, versus 2.31G
  cycles ≈ 4.3 min stock — **5.5x per iteration**. Same end state, no
  Sad Mac tripwire, no monitor entry.
- Generator: `docs/tools/make-fastboot-rom.sh` (used by
  `make fastboot`); it validates the input checksum and the expected
  `6606` bytes before patching.

## Open items

  biggest fixed cost; unidentified. Trace window
  `--trace-after 39000000 --stop-at-pc 40807116,40807117` would name

- The warm continuation's block fields at `+$1E`/`+$26` are
  understood only as far as "mismatch tolerated"; if fastboot ever

  `$01FFFF00..$01FFFFFF` at ~1.7G cycles) and replay it instead of
  patching the branch.
